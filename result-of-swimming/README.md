# Result of Swimming データ収集・集計基盤

`result.swim.or.jp` から レース結果 / LAP を収集し、SwimHub 本番DBには
**集計済みの LAP 統計のみ** を保存するパイプライン。

現状: **Phase 0 (調査) / Phase 1 (純粋ロジック) / Phase 2 (パイプライン一式) 完了**。
実データで 取得→パース→検証→集計→SQL生成 まで通っている。

---

## Phase 0 調査結果 (2026-08-19 実測)

### 1. サイト構成

Next.js の **静的エクスポート** SPA (`nextExport: true`)。HTML には
データが一切含まれず、全て内部 JSON API から取得している。
したがって **HTML パースではなく JSON API を叩くのが正解** で、
サイト負荷も桁違いに軽い (HTML/JS/画像を落とさない)。

- `robots.txt` は **404** (クロール指示なし)
- ブラウザ用の `利用規約` / 著作権表記はフロントエンドの bundle 内に存在しない
- **headless Chromium は全パス 403**、素の HTTP クライアントは 200
  (既存 `swim-hub/scraping/` が `--headed` 必須なのはこれが理由)

### 2. API

ベース URL: `https://result.swim.or.jp/api/v1` (認証なし・同一オリジン)

**レスポンスヘッダーに明示的なクォータが載っている:**

```
x-ratelimit-limit: 3000
x-ratelimit-remaining: 2525
```

→ crawler は `x-ratelimit-remaining` を読んで自己抑制する。
これを無視しない限り、回避行為は一切不要。

#### クロールに使うエンドポイント

| 用途 | エンドポイント |
|---|---|
| 大会一覧 (ページング) | `GET /games?year={年度}&page={n}` |
| 種目ツリー | `GET /games/{game_code}/races` |
| 組一覧 | `GET /games/{gc}/heats/genders/{g}/swimming_styles/{s}/distances/{d}/classes/{c}` |
| **レース結果 + LAP** | `GET /games/{gc}/results/genders/{g}/swimming_styles/{s}/distances/{d}/classes/{c}/race_divisions/{rd}/heats/{h}` |

ページングは Laravel 形式 (`data` / `links` / `meta.last_page` / `meta.total`)。

#### enum (自己記述的: `{code, name}` で返る)

| 種別 | 値 |
|---|---|
| `gender` | 1=男子, 2=女子 |
| `swimming_style` | 1=自由形, 2=背泳ぎ, 3=平泳ぎ, 4=バタフライ, 5=個人メドレー, **6=フリーリレー, 7=メドレーリレー** |
| `distance` | 2=50m, 3=100m, 4=200m, 5=400m, 6=800m, 7=1500m |
| `waterway` | **1=長水路(50m), 2=短水路(25m)** |
| `game_status` | 5=記録確定 (これのみ収集対象) |
| `race_division` | 1=予選, 2=タイム決勝, 3=B-決勝, 4=決勝(A-決勝), 5=スイムオフ |
| `reason_code` | **0=正常, 1=棄権(DNS), 2=失格(DSQ)** |

> `waterway` は既存 `scraping/types.ts` のコメント (`1=短水路, 2=長水路`) と**逆**。
> code をハードコードせず `name` から判定するのが安全。

### 3. LAP データ ★最重要

`lap_detail[]` に入る。

```json
"lap_detail": [
  {"lap_distance": 50,  "passing_time": {"record": "0:23.74"}, "50m_record": {"record": "0:23.74"}},
  {"lap_distance": 100, "passing_time": {"record": "0:49.52"}, "50m_record": {"record": "0:25.78"}}
]
```

- `passing_time.record` = **累積**通過タイム
- `50m_record` / `100m_record` / `200m_record` = 区間タイム (累積から差分計算しても一致)

**LAP 粒度は長水路・短水路とも常に 50m の倍数。25m split は存在しない。**

| 距離 | LAP本数 | 実測 |
|---|---|---|
| 100m | 2 | 50 / 100 |
| 200m | 4 | 50 / 100 / 150 / 200 |
| 400m | 8 | 50…400 |
| 1500m | 30 | 50…1500 |

→ 目標LAP機能は **50m刻み** が上限。25m刻みは本データ源からは生成できない。

**決定 (2026-08-19, ユーザー判断): 25m LAP は対象外。50m刻みのみで実装する。**
50m LAP の機械的2分割などによる擬似25mデータは生成しない。
`race_pace_models.split_interval` は当面 **常に 50** となるが、
unique 制約のキーには含めたまま残す (後から追加すると
unique index の作り直しと全行の再キー付けが必要になるため)。

したがって生成される理想LAPは:

```
男子 長水路 100m自由形 目標 50.00
  50m   24.00
  100m  50.00
```

### 4. タイム表現

- `result_time`: `"49.52"` (ss.cc) / `"3:49.31"` (m:ss.cc) / `"15:27.00"` (mm:ss.cc)
- `passing_time.record`: 先頭が `0:` の m:ss.cc
- DSQ/DNS 時は `""` (空文字)
- `record_ms` という名前のフィールドが bundle 内にあるが、これは
  **クライアントがグラフ用に計算した「秒」** で API のフィールドではない

### 5. 年齢 / カテゴリ

実年齢は返らない。代替となるのは2つ:

- `swimmers.school_class` = `{code:4, name:"大学", school_grade:[3]}` (**個人**の学種/学年)
- `class` = 大会側のカテゴリ。大会ごとに意味が変わる (`"１部"` / `"高校"` など)

### 6. 個人情報

`swimmers.swimmer_name` / `swimmer_code` / `entry_group` が含まれる。
**パース時に破棄し、一切保存しない。** 残すのは `school_class` のみ。

`graphs` フィールドはレスポンスの **81%** を占めるが用途なし → パース時に破棄。

### 7. `heat: 100` は集約レスポンス ★効率

組一覧が `heats: [100, 1, 2, ...]` を返すとき、`heat=100` は
**その division の全組をまとめた1レスポンス** (実測: 60名 = 組1〜6の和集合、
各行に本来の `heat` 値が入る)。個別組の完全な上位集合であることを確認済み。

→ `100` があれば **それ1本だけ取得**する。上の実測例では 6リクエスト → 1リクエスト。
決勝など `heats: [1]` のみの division は個別取得。

### 8. 規模見積

| 指標 | 実測値 |
|---|---|
| 大会数 (FY2026) | 1,106 (`meta.total`) |
| 取得可能年度 | 2010 は可 / 2005・2003 は 422 → 下限は 2006〜2010 の間 |
| 出場者数 (記録確定分の標本100大会) | 平均 342 / 中央値 190 / 最大 1,318 |
| 1大会あたりのリクエスト (大規模大会 実測) | 結果 125 + 組一覧 52 + 種目1 = **178** |

集約 heat 戦略込みで平均 ~90 req/大会と仮定すると、1年度で約10万リクエスト。
**全年度の全件取得は非現実的**なので、統計に必要な標本数が埋まる範囲に絞る。

### 9. 規約・著作権 (2026-08-19 確認済み)

`swim.or.jp` は**旧ドメイン**で証明書が期限切れのまま放置されている。
連盟の現行サイトは **`aquatics.or.jp`**。

現行サイトのフッターは `プライバシーポリシー` / `アンチ・ドーピング` /
`暴力行為等相談窓口` / `リンク集` の4つのみで、
**利用規約・サイトポリシー・免責事項のページは存在しない。**
プライバシーポリシーも個人情報の取扱い専用でコンテンツの二次利用に言及がない。

サイト全体で関連する記述は以下だけ:

> 著作権は、公益財団法⼈⽇本⽔泳連盟に帰属します。

フッターに `© Copyright 2006-2026 Japan Aquatics`。

| 項目 | 結果 |
|---|---|
| 利用規約 | 存在しない |
| robots.txt | 404 (指示なし) |
| スクレイピング/robots 禁止条項 | なし |
| レート制限 | `x-ratelimit-limit: 3000` を公開 |
| 著作権 | サイト掲載物は連盟に帰属と明記 |

禁止条項はないが著作権は主張されているため、論点は取得の可否ではなく
**取得物の扱い**。本設計は既にそこを回避している:

- 生データは本番DBに保存しない (保存するのは LAP比率の median 等の集計値のみ)
- 個人情報はパース段階で破棄する
- 個々のレース結果を再配布しない

**残る判断 (法務判断であり実装側では決めない):**

1. 連盟への許諾連絡を行うか (規約が無い=黙認とも読めるが、商用プロダクトの
   元データにするなら事前連絡が最も安全)
2. 機能画面に出典表記 (「データ出典: 公益財団法人日本水泳連盟」) を出すか

## 使い方

```bash
# 取得 (--limit は結果リクエスト数の上限。段階的に上げる)
pnpm ros:crawl --year 2026 --games 1 --limit 10
pnpm ros:crawl --year 2026 --games 3 --limit 60

# クレンジング結果の確認
pnpm ros:validate

# 集計 (既定 min-samples=30)
pnpm ros:aggregate
pnpm ros:aggregate --min-samples 5 --age-mode school_class

# Supabase 投入用 SQL の生成
pnpm ros:export

# テスト
pnpm ros:test
```

取得済み URL はキャッシュから返るため、**何度実行しても取り直さない**。
途中で止めても次回は続きから進む。パーサを直した場合も
キャッシュがあるので再取得は不要。

出力は `data/` (gitignore 済み):

| ファイル | 内容 |
|---|---|
| `data/cache/` | 生レスポンス (gzip)。これが「取得済み集合」を兼ねる |
| `data/journal.jsonl` | fetch / retry / throttle / give_up の記録 |
| `data/races.jsonl` | パース済み RawRace (1行1件、DuckDB が直接読める) |
| `data/models.json` | 集計済み RacePaceModel |
| `data/race_pace_models.sql` | Supabase 投入用 upsert |

| 結果リクエスト数 | 68 |
| 取得できたレース | 1,135 件 (**18.9 件/リクエスト**) |

| disqualified (棄権/失格) | 42 件 (3.7%) |

### ★ サンプル密度 — 拡大時の一番の制約

100m 以上の有効レース 658 件を条件別に割ると:

| 指標 | 実測値 |
|---|---|
| 種目グループ数 (gender×pool×stroke×distance) | 22 |
| bucket 込みグループ数 | 483 |
| **1グループあたり平均** | **1.36 件** |
| 最大 / 中央 | 6 件 / 1 件 |
| n>=30 を満たすグループ | **0** |

0.5秒刻みの bucket は非常に細かく、大会2件では中央値がまだ意味を持たない。
`min_samples=30` を満たすには概算で **10万レース規模** が必要
(= 約5,300 結果リクエスト。1.5秒間隔で **2〜3時間**)。
現実的には1〜2年度分の記録確定大会を回す想定。

希少種目 (女子1500m 等) は年度を増やしても埋まらないため、
`TIME_BUCKET_CONFIG` で距離ごとに bucket 幅を広げるか、
検索時のフォールバック階層 (隣接bucket → 種目全体) で吸収する。

## 設計判断の記録

- **crawl frontier に SQLite を使わなかった**
  当初 SQLite で取得済み状態を管理する設計だったが、(1) Node 20 に
  `node:sqlite` が無く、(2) 「訪問済み集合」は内容アドレス指定キャッシュが
  既に表現しているため、native 依存を足す理由が無かった。
  失敗の記録は `journal.jsonl` が担う。結果として**ランタイム依存ゼロ**。

- **集計は TS で実装し、DuckDB は拡大時の受け皿に留めた**
  PoC 規模ではメモリ上の集計で足り、native 依存を避けられる。
  `percentile` を DuckDB の `quantile_cont` と同一定義 (線形補間) に
  揃えてあるので、`races.jsonl` を Parquet 化して集計を SQL へ移しても
  同じ数値が出る。`aggregate()` は `Iterable<RawRace>` を受けるので
  ストリームへの差し替えも可能。

- **この package は CJS**
  `apps/shared` に `"type": "module"` が無く、ESM から named import
  すると `default` だけになる。`apps/shared` 側に手を入れる方が
  影響範囲が広いので、こちらを CJS に合わせた。

- **50m 種目はモデルにしない**
  途中計時が1点 (ゴール) のみで比率が必ず 1.0 になり、
  「理想LAP = 目標タイム」という情報量ゼロの行になるため除外する。

- **`/scraping/` と違い、この package はソースを git 追跡する**
  `.gitignore` の `/scraping/` はディレクトリ全体を無視しているが、
  こちらはテスト付きの実装なのでソースは追跡し、
  `data/` と `node_modules/` のみ無視する。

### ★ アクセスをブロックされた (要判断)

**`02:13:25Z` を境に全リクエストが 403 になり、以降回復していない。**

- 200 の最後: `02:13:25Z` / 403 の最初: `02:13:26Z` — 境界が1秒
- 403 は109件すべてこの直後の2分50秒に集中。**特定の大会の問題ではない**
- 打ち切り時点で `x-ratelimit-remaining` は **2,980 残っていた**
  → 公開クォータとは別の、文書化されていない保護機構
- 事後確認: **トップページ (`/`) すら 403 / body 0B / rate-limit ヘッダーも消滅**
  → パス単位ではなく **IP 単位のブロック**
- 「headless Chromium は全パス403」と同じ挙動

発動条件の推定: スリープ抑止をかけて**初めて連続高速稼働した約20分後**。
1.5秒間隔 (実効 0.43 req/s) でも、持続的な自動アクセスは許容されないと見られる。

**回避策は実装していない** (UA偽装・プロキシ・分散などは行わない)。
再開の可否はサイト運営者への確認が必要。

対策として実装したもの:
- **403 が5回連続したら中断**する (`consecutiveBlockLimit`)。
  今回は気づかず109回叩き続けたため、同じことを繰り返さない
- **取得失敗を「個人種目なし」と記録しない**。
  403 の54大会が「個人種目なし」と記録され原因を誤診したため分離した

### 欠測の途中計時は `0` で返る

400m個メの実例:

```
 50m cum= 30640   100m cum= 68760   150m cum=     0  ← 欠測
200m cum=169340   ...
```

`null` や空文字ではなく **`0`**。1箇所の欠測が
「-68,760ms の負ラップ」と「+169,340ms の巨大ラップ」の**2本を同時に壊す**。

`valid` 31,245件を検算した結果、汚染は **0件**:

| 検査 | 結果 |
|---|---|
| cumulative に 0 を含む | 0 |
| 累積が単調増加でない | 0 |
| lap合計が最終タイムと乖離 >50ms | 0 |
| LAP本数が distance/50 と不一致 | 0 |

欠測を含む1,386件は全て除外側 (missing_split / disqualified / invalid_time) に落ちている。

### 生成モデルの妥当性

水泳の常識と一致しており、パイプラインが正しく動いている根拠になる。

```
200m自由形 (15 bucket でほぼ同一)   22.8% / 25.3% / 26.1% / 25.7%
  → 飛び込みで速く入り、3本目が最遅、最後に上げる典型形

200m個人メドレー                    21.2% / 26.5% / 29.5% / 22.8%
  → バタフライ → 背泳ぎ → 平泳ぎが最遅 → 自由形で復活 (正しい種目順の特性)

400m自由形  11.2% / 12.3% / 12.7% / 12.8% / 12.8% / 13.0% / 12.9% / 12.5%
  → 飛び込み → 中盤最遅 → ラストスパート
```

カバレッジ: 100m が63モデル、200m が16、400m が1。
男子48 / 女子32、すべて長水路。短水路と長距離は標本不足。

## bucket 幅の最適化 (2026-08-20)

ブロック中で追加取得ができないため、取得済み32,631件から
モデル数を増やす方向で bucket 幅を実測で詰めた。

| 幅 (100m) | モデル数 | p75-p25 平均幅 (ばらつき) |
|---|---|---|
| 0.5秒 (当初) | 80 | 0.515 pt |
| **1.0秒 (採用)** | **212** | 0.533 pt (**+3.5%**) |
| 2.0秒 | 217 | — |
| 4.0秒 | 157 | — |

カバレッジが 2.65倍 になる一方、ばらつきの増加は 3.5% に留まった。
比率パターンも変わらない (200m自由形: 23.1/25.3/26.1/25.6 →
23.2/25.4/25.9/25.6)。4.0秒まで広げるとモデル数が減る (グループが
統合されてしまう) ので 1.0秒が最適点。

`TIME_BUCKET_CONFIG` の既定値を倍にした。標本が増えたら狭める方向に戻せる。
